# macOS: отслеживание окон (CAPRI-08)

Дата: 2026-10-28. Проверено на Apple M4, macOS 26 (Darwin 25.6), один внешний монитор 2560×1440 @1x, Electron из `node_modules` проекта.

Это изолированный прототип. В `main.js` и `windows.js` он не подключён, это работа CAPRI-09.

## Итог

Геометрию чужих окон, их z-порядок и активное окно на Apple Silicon можно получать **без системных разрешений**. Хватает публичных `CGWindowListCopyWindowInfo` и `NSWorkspace`. Они работают в маленьком Swift-helper, который Electron запускает дочерним процессом, так же как сейчас на Windows запускается `windows.ps1`. Координаты helper совпадают с DIP-координатами Electron, пересчитывать масштаб не нужно.

Для первого Mac-контракта доступны `fg` и `wins`. Поля `taskbar`, `ai`, `game`, `usb` и `plug` на macOS остаются пустыми по умолчанию, ограничения описаны ниже.

## Файлы прототипа

| Файл | Назначение |
|---|---|
| `src/main/mac/capri-windows.swift` | helper: печатает JSON-строку при каждом изменении |
| `src/main/mac/window-watch.js` | адаптер: `startMacWindowWatch({ overlay, onUpdate })` с тем же контрактом, что `startWindowWatch()`, плюс чистые `parseLine()` и `toUpdate()` |
| `tests/mac-window-watch.test.js` | тесты парсинга, нормализации, фильтра overlay, отказа helper и ограничения перезапусков (`npm test`, на любой ОС) |
| `scripts/mac-window-scenario.js` | реальный сценарий на Mac: свои тестовые окна, перемещение, сворачивание, закрытие, полный экран |
| `tools/mac-window-fixture.swift` | тестовые окна для сценария, управляются через stdin |
| `scripts/mac-window-probe.js` | проверка внутри Electron: дисплеи Electron против helper, фильтрация настоящего BrowserWindow |

Скомпилированные бинарники не коммитятся: `src/main/mac/bin/` есть в `.gitignore`, fixture собирается во временный каталог.

## Выбор API

| Вариант | Разрешения | Почему выбран или нет |
|---|---|---|
| **`CGWindowListCopyWindowInfo` + `NSWorkspace.frontmostApplication`** | нет | **Выбран.** Отдаёт номер окна, PID владельца, уровень, прозрачность и рамку в глобальных точках, порядок спереди назад, только текущий Space. Названия окон без Screen Recording не отдаёт, и они нам не нужны. |
| Accessibility API (`AXUIElement`, `AXObserver`) | Accessibility | Даёт события перемещения, свёрнутое/zoomed состояние и фокусное окно внутри приложения. Требует, чтобы пользователь вручную включил Capri в настройках. Для сидения не обязателен; в CAPRI-09 может стать необязательным улучшением, если опрос окажется слишком медленным. |
| ScreenCaptureKit (`SCShareableContent`) | Screen Recording | Отклонён: ради геометрии нужен захват экрана, это прямо запрещено задачей. |
| Нативный npm-модуль (N-API, `node-gyp`) | нет | Отклонён: новые npm-зависимости и пересборка под каждую ABI Electron. Падение модуля роняет main-процесс. |
| `osascript` / System Events | Accessibility + Automation | Отклонён: два запроса разрешений, медленно (сотни миллисекунд на вызов). |
| Приватные CGS/SkyLight API | нет | Отклонены: недокументированы, ломаются между версиями macOS, риск при нотаризации. |

Почему отдельный процесс на Swift, а не модуль внутри Electron: helper не зависит от ABI Node/Electron. Его падение не затрагивает приложение, адаптер просто остаётся без данных. Схема совпадает с уже принятой для Windows (отдельный процесс, построчный JSON, перезапуск не больше трёх раз). `swiftc` входит в Xcode Command Line Tools, бинарник получается около 95 КБ и использует только системные фреймворки.

## Разрешения

- Helper **не требует ни одного разрешения** и ни одно не запрашивает. Ни один используемый вызов не показывает системный диалог.
- Проверено честно, без унаследованных прав терминала. Терминал на тестовой машине имеет Screen Recording и Accessibility, поэтому helper запускался как отдельный «ответственный процесс» (`posix_spawn` с `responsibility_spawnattrs_setdisclaim`, одноразовый launcher в scratchpad, в репозиторий не входит). Результат `--probe`: `screenRecording:false`, `accessibility:false`. Список окон и рамки при этом те же (85 окон в системе, 22 подходящих), `fg` определяется.
- Названия окон без Screen Recording система почти не отдаёт: 2 из 85, и это системные окна. Helper `kCGWindowName` и имена приложений не читает вообще. Только режим `--probe` считает, у скольких окон есть название, и не печатает ни одного.
- Если Capri в будущем понадобится Accessibility, объяснять это пользователю и ждать, что он включит его сам. Без разрешения работает текущий способ, базовый overlay остаётся как есть.

## Формат

Helper, одна строка на изменение:

```json
{"v":1,"fg":73476,"displays":[{"id":2,"x":0,"y":0,"w":2560,"h":1440,"scale":1.0}],
 "wins":[{"id":73476,"x":319,"y":30,"w":1920,"h":952,"max":false,"full":false}]}
```

- `id`: `CGWindowID`, то же число, что `NSWindow.windowNumber`. Совпадает с `id` в `getMediaSourceId()` у Electron (`window:<id>:0`).
- `wins`: окна текущего Space спереди назад. Остаются только окна уровня 0 (обычные окна приложений; меню, Dock, панели и overlay Capri на уровне `screen-saver` отсеиваются), с прозрачностью от 0.05, не меньше 200×120, не больше 40 штук. Это те же пороги, что в `windows.ps1`.
- `fg`: верхнее окно уровня 0 у активного приложения. Если у активного приложения нет такого окна на экране (сама Capri, рабочий стол, экран блокировки), будет `null`. На Windows в этих случаях пришёл бы handle окна, которого нет в `wins`. Для renderer это равнозначно: `wins.find()` ничего не находит.
- `max`: рамка совпадает с видимой областью экрана (без меню и Dock, допуск 4 pt) или со всем экраном. Это эвристика, состояния zoom из CoreGraphics не получить.
- `full`: рамка совпадает со всем дисплеем, то есть окно в полноэкранном режиме. Новое поле, на Windows его нет. renderer его пока не читает.
- `displays`: нужны для проверок и CAPRI-09. `id` равен `CGDirectDisplayID`, а это тот же `display.id`, что в Electron (на тестовой машине `2` в обоих).

Адаптер (`toUpdate`) отдаёт форму Windows: `{ fg, taskbar:false, ai:[], game:null, usb:[], plug:null, wins:[{id,x,y,w,h,max,full}] }`. Координаты окон переводятся в систему overlay, остаются только окна, пересекающие его экран. Неизвестные поля строки helper отбрасываются, поэтому название окна дальше main-процесса не уйдёт, даже если когда-нибудь появится в выводе.

## Координаты

- CoreGraphics отдаёт рамки в **глобальных точках**: начало в левом верхнем углу главного дисплея, y растёт вниз. Electron на macOS использует те же точки (DIP) в `screen` и `BrowserWindow.getBounds()`. Поэтому адаптер только вычитает `overlay.getBounds()`, `screenToDipRect` не нужен.
- Проверено в Electron (`scripts/mac-window-probe.js`): `screen.getAllDisplays()` = `{id:2, bounds:0,0 2560×1440, workArea:0,30 2560×1312, scale:1}`, helper = `{id:2, 0,0 2560×1440, scale:1}`. Развёрнутые окна приходят как `0,30 2560×1312`, то есть ровно `workArea`.
- **Retina:** рамки CoreGraphics всегда в точках, независимо от `backingScaleFactor`, так что на 2x пересчёт тоже не нужен. Физически **не проверено**: подключён только экран 1x. Helper отдаёт `scale` каждого дисплея, по нему это можно будет проверить.
- **Отрицательные координаты:** проверено с окном, выдвинутым за левый край (`-250,300 700×400` приходит как есть и остаётся в update overlay). Дисплеи левее или выше главного дают отрицательные глобальные координаты по самому устройству системы; пересчёт в overlay на таком дисплее покрыт тестом. На втором физическом мониторе **не проверено**.

## Жизненный цикл

Helper опрашивает список окон каждые 150 мс и печатает строку только при изменении. Смену активного приложения и конфигурации экранов он сообщает сразу, по уведомлениям `NSWorkspace` и `NSApplication`. Помимо этого helper завершается, когда закрывается его stdin (`--watch-stdin`, Capri упала) или когда пропадает родительский процесс (`--parent`).

| Событие | Что видно | Задержка в сценарии |
|---|---|---|
| Окно открыто | появляется в `wins`; во время анимации открытия рамка на несколько точек меньше, затем приходит итоговая | 130–180 мс до точной рамки |
| Перемещено | новая рамка | 80–110 мс |
| Свёрнуто | исчезает из `wins` | ~210 мс |
| Развёрнуто из Dock | возвращается, сначала промежуточные кадры анимации | ~310 мс |
| Приложение скрыто (Cmd-H) / показано | окна исчезают / возвращаются | 25–50 мс |
| `orderOut` / закрыто | исчезает | 180–210 мс |
| Приложение завершилось | все его окна исчезают | ~25 мс |
| Полный экран | окно в отдельном Space с рамкой дисплея, `full:true`, `max:true`; остальные окна пропадают из списка (22 → 0) | ~650 мс |
| Выход из полного экрана | рамка и остальные окна возвращаются | ~680 мс |
| Фокус на другое окно | `fg` меняется сразу | < 1 тика |

Свёрнутое, скрытое, закрытое окно и окно на другом Space выглядят одинаково: оно пропало. Для CAPRI-09 (сойти или упасть, когда окна нет) этого достаточно. Различать причины без Accessibility нельзя.

Экран блокировки: активным приложением становится `loginwindow`, поэтому `fg` равен `null`. Окна при этом остаются в списке. Анимации закрытия и открытия, пока дисплей спит, могут зависнуть на промежуточном кадре: закрытое окно иногда оставалось в списке больше 6 с. Значит, на время блокировки watcher лучше ставить на паузу (это относится к CAPRI-07), а не верить снимкам.

Нагрузка: при 150 мс и 22 окнах helper использовал 0.24 с CPU за 30 с (около 0.8 % одного ядра) и около 24 МБ RSS. Если этого окажется много, интервал можно поднять (`--interval`) или опрашивать чаще только во время движения.

## Ограничения

- **`ai`:** у Windows это сопоставление заголовка активного окна со списком имён. На macOS без Screen Recording заголовков нет. Возможная замена без разрешений: bundle id активного приложения (например, приложения ChatGPT), но не вкладки браузера. Не реализовано, отдельное решение для CAPRI-09 или позже.
- **`game`, `usb`, `plug`:** не реализованы, в задачу не входят.
- **`taskbar`:** аналога нет. Dock и строка меню не на уровне 0, а overlay на macOS уже выше них.
- **Spaces:** видны только окна текущего Space. Проверен переход в полноэкранный Space и обратно. Ручное переключение между обычными Spaces, Mission Control и Stage Manager **не проверялись**: без пользователя или приватных API их не вызвать.
- **Фокус в сценарии:** начиная с macOS 14 приложение получает фокус, только если активное приложение его уступает. Когда сценарий запускался при заблокированном экране, проверки фокуса и полного экрана честно отмечались как SKIP. Полный прогон прошёл после разблокировки.
- **`max`** остаётся эвристикой по рамке.
- Окна на уровнях выше 0 (плавающие панели, «поверх всех») сидением не считаются. Так задумано, но некоторые приложения держат главное окно на другом уровне.

## Сборка и упаковка

Нужны Xcode Command Line Tools (`xcode-select --install`), npm-зависимостей нет.

```sh
swiftc -O -target arm64-apple-macos12.0 -o src/main/mac/bin/capri-windows src/main/mac/capri-windows.swift
src/main/mac/bin/capri-windows --probe   # какие разрешения есть у процесса (ничего не запрашивает)
src/main/mac/bin/capri-windows --once    # один снимок
node scripts/mac-window-scenario.js      # реальный сценарий: собирает недостающее, на несколько секунд открывает тестовые окна и полноэкранный Space
npx electron scripts/mac-window-probe.js 10   # внутри Electron: дисплеи и фильтрация overlay
```

Минимальная система: macOS 12 (`minos 12.0`, как у Electron), только arm64. Линкуются только системные фреймворки и Swift runtime из ОС.

Для CAPRI-09 (сейчас не сделано):

- Собирать helper на macOS-раннере CI перед `electron-builder --mac`, а не хранить бинарник в git.
- Класть его в `src/main/mac/bin/` и добавить `src/main/mac/bin/**` в `asarUnpack`. Адаптер уже заменяет путь `app.asar` на `app.asar.unpacked`, как это делает `windows.js`.
- electron-builder подписывает исполняемые файлы внутри бандла с hardened runtime. Entitlements helper не нужны. Проверить подпись (`codesign -dv`) и нотаризацию на упакованном `.app`.
- Пока helper не собран, адаптер возвращает `{ available:false }`, а `onUpdate` не вызывается: базовый overlay работает как раньше. Локальная сборка без helper не ломается. Учесть, что `files: src/**` возьмёт в пакет и `.swift`-исходник, и локально собранный бинарник (внутрь asar, где он не исполняется).

## Что проверено

- `npm test`: 17 тестов, все проходят, из них 6 новых для адаптера.
- `node scripts/mac-window-scenario.js` на разблокированной машине: 23/23 без ошибок. Совпадение дисплеев с NSScreen, точные рамки после анимации, отрицательный x, z-порядок, `fg` при открытии и переключении, перемещение, сворачивание и развёртывание, Cmd-H, `orderOut`, закрытие, полный экран (свой Space, `full`/`max`, остальные окна скрыты) и выход из него, завершение приложения, выход helper по закрытию pipe. Второй дисплей: SKIP.
- Тот же сценарий при заблокированном экране: геометрия, перемещение, сворачивание и закрытие проходят (закрытие нестабильно, см. выше); фокус и полный экран: SKIP.
- `electron scripts/mac-window-probe.js`: дисплеи Electron и helper совпадают. Настоящее прозрачное click-through `BrowserWindow` на обычном уровне helper без фильтра видит, а адаптер через `--self-window` его отсеивает.
- Helper без унаследованных разрешений: геометрия и `fg` есть, разрешения не запрашиваются.
- Helper завершается после `SIGKILL` родителя: и по закрытому stdin, и по `--parent` (в пределах ~3 с).

## Что не проверено

- Retina (2x) и несколько мониторов: подключён один экран 1x.
- Дисплей левее или выше главного (отрицательные координаты целого экрана): только тест на числах.
- Ручное переключение Spaces, Mission Control, Stage Manager.
- Перетаскивание окна мышью: проверено программным `setFrame`. Частота обновлений при непрерывном перетаскивании ограничена опросом 150 мс.
- Упакованное приложение, подпись и нотаризация helper: это CAPRI-09.
- Работа с настоящим персонажем (renderer): это CAPRI-09.
